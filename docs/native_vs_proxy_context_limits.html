How the 1M context limit is handled — native CC vs our proxy

What Anthropic + Claude Code do out of the box when a session approaches the 1M-token cap, where the failure modes are, and what the local proxy changes about it.

1 · Native flow no proxy

Anthropic enforces the cap at the API layer — they don't pre-emptively warn you, they just reject. The native handling on the CC side is mostly a "manual escape hatch."

The two pitfalls Anthropic doesn't warn you about

Pitfall 1 — /compact can deadlock
When the conversation is already too big, /compact itself fails with "Conversation too long" — the exact situation where you need it most. This is tracked in claude-code#23047 and #26317. Result: /clear becomes the only escape, losing all your context.
Pitfall 2 — Auto-compact thrashing
CC has automatic compaction when approaching the limit (controlled by the DISABLE_AUTO_COMPACT env var). It tries to summarize before you hit the cap. But on huge sessions, the summary itself is still over the cap → CC re-summarizes → still over → eventually CC gives up and shows the same red banner anyway. Anthropic's docs note: "Claude Code stops auto-compacting after a few attempts and shows an error instead of looping."

2 · With our proxy claude_proxy.py

The proxy intercepts every request between CC and api.anthropic.com. When the conversation grows past a configurable trigger, it slices old turn groups out of the request body before forwarding, so the conversation Anthropic sees is always under the cap. The CC client has no idea trimming happened.

What the proxy doesn't try to be

  • Not a summarizer. Old turns aren't compressed — they're dropped from the request entirely. /compact's job is different (LLM-condense into a recap); the proxy just slices.
  • Not visible to CC. CC keeps its full transcript on disk (the JSONL file). The proxy only changes what's actually sent to Anthropic per turn.
  • Not lossy on cache. Between trim events the byte prefix is stable, so Anthropic's prompt cache hits at ~99% — exactly like un-trimmed traffic.

3 · Side by side

Aspect Native CC (no proxy) With claude_proxy.py
When hits 1M cap 400 error → red banner → manual recovery Never reaches it — proxy slices before forwarding
Manual intervention User types /clear or /compact None. Old turns drop silently.
Context retained on hit /clear = nothing. /compact = LLM summary of full history. Most recent ~400K tokens of real conversation, verbatim.
Old turn fidelity After /compact: high-level recap only — specifics lost. Old turns gone entirely (no summary). Recent context preserved exactly.
/compact failure mode Can deadlock ("Conversation too long" — see #23047) Doesn't apply — no compact needed
Auto-compact thrashing Possible on huge sessions; fails to a banner anyway Doesn't apply — proxy never triggers the cap
Cache hit rate Resets every /compact or /clear ~99% between shifts; one cache-miss per shift (~1 per 100-250 turns)
"Why is my session broken?" debuggability Banner says "context limit" — true symptom, no detail All forwards logged with KST timestamps + token counts in proxy.log; failures dump full request/response to JSON

4 · The trade-off

native compact wins on

  • Long-term recall. If you need to reference something from 100 turns ago, an LLM summary still contains it (compressed). The proxy will have dropped it entirely.
  • Single-session reasoning. A compacted recap can preserve narrative arc; raw slicing breaks "earlier we decided…" references.

proxy slicing wins on

  • Active coding sessions. Recent turns matter most. Older "let me read this file" turns are usually safe to lose.
  • Zero friction. No /clear, no compact wait time, no deadlock risk. Session feels infinite.
  • Cache stability. 99% prompt-cache hit between shifts = fast turns and cheaper bills.

For the use case the proxy was designed for — long all-day coding sessions on a specific PR — slicing is the right trade. For "research" sessions that need to recall details from far back, native /compact is still the better tool (when it works).
