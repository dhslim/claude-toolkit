Anatomy of a POST /v1/messages request

The wire format Claude Code sends to Anthropic — headers + JSON body — annotated with the real payloads we captured from your own machine. Verified against platform.claude.com/docs.

Every turn you take in Claude Code becomes one HTTPS request: POST https://api.anthropic.com/v1/messages. It has exactly two parts — an envelope (headers) and a letter (JSON body) — split by a single blank line. Get those two straight and the whole API stops being mysterious.

HEADERS — the envelope

Metadata about the request: who you are (authorization), which API contract (anthropic-version), which beta features (anthropic-beta), the content type, and SDK telemetry. The server reads these to route & authorize.

JSON BODY — the letter

The actual ask: which model, the messages history, max_tokens, the system prompt, tools, thinking… This is where the request parameters live — there is no "model header"; the model is a body field.

Here is a real (small) request from your Claude Code, with the auth token redacted and the body collapsed:

POST /v1/messages?beta=true HTTP/1.1            # request line
Host: localhost:9999                              # (your proxy; → api.anthropic.com upstream)
Authorization: Bearer <redacted>
Content-Type: application/json
anthropic-version: 2023-06-01
anthropic-beta: claude-code-20250219,oauth-2025-04-20,interleaved-thinking-2025-05-14,…
User-Agent: claude-cli/2.1.193 (external, cli)
X-Stainless-Lang: js     X-Stainless-OS: Windows     X-Stainless-Retry-Count: 0
                                                  # ← blank line = divider
{ "model": "claude-opus-4-8", "max_tokens": 32000,
  "system": […], "messages": […], "thinking": {…}, "metadata": {…} }

1 · The headers (the envelope)

Headers carry identity, versioning, and feature flags — never the request content. Required vs optional below; required conditional optional.

HeaderWhat it does
HostreqThe target authority. A proxy must rewrite it to api.anthropic.com so it matches the upstream TLS vhost (your client sent localhost:9999).
Authorization: Bearer …
or x-api-key		cndAuth. Send exactly one: x-api-key (Console API key) or Authorization: Bearer (a short-lived OAuth token — which is what Claude Code / Max uses). Not interchangeable.
anthropic-versionreqPins the API contract — request params, response shape, SSE format, error conditions. Current: 2023-06-01. Within a version Anthropic only adds (new optional inputs, new enum values), so parse defensively. SDKs set it for you.
anthropic-betaoptOne comma-separated list of dated feature flags (feature-YYYY-MM-DD). Opts into experimental features. An unknown flag → invalid_request_error "Unsupported beta header". (See §6 for the date convention.)
content-typereqMust be application/json.
Content-LengthcndByte length of the body. A proxy that edits the body must recompute it. (Requests cap at 32 MB → 413 request_too_large.)
User-Agent, x-stainless-*optSDK telemetry (language, OS, package version, retry count). Not part of the API contract — the server ignores them; a proxy may forward or drop them.
anthropic-dangerous-direct-browser-accesscndOnly for direct browser/CORS calls. Its scary name is deliberate — it enables CORS but does not make a client-embedded key safe.

End-to-end vs hop-by-hop

Headers split into two kinds, and this is why a proxy can safely sit in the middle: end-to-end headers (authorization, anthropic-version, anthropic-beta, content-type) describe the message and must be forwarded verbatim. Hop-by-hop headers (Host, Content-Length, Connection, Transfer-Encoding) describe this one TCP leg and are re-made for the next leg. Re-enveloping the request never touches the letter inside.

2 · The body — top-level fields (the letter)

The body is one JSON object. Three fields are required — model, messages, max_tokens — everything else is optional. Note max_tokens has no default, and the model goes here in the body, not in a header.

FieldTypeMeaning
modelreqstringWhich brain, e.g. claude-opus-4-8. Picks the model — not the window size (that's native or set by a beta header). See §7 for the subtle "[1m]" twist.
messagesreqarrayThe conversation (see §3). Up to 100,000 messages; consecutive same-role turns are merged. There is no system role here.
max_tokensreqintegerHard cap on tokens generated. No default — you must supply it. The model may stop earlier.
systemoptstring | block[]System prompt, as a top-level field (not a message). Array form lets you attach cache_control per block. (§4)
temperatureopt0.0–1.0Randomness. Default 1.0. Range is 0–1 (not 0–2). Even 0.0 isn't fully deterministic.
top_p / top_koptnumber / intNucleus / top-k sampling. No default; advanced use only — don't tune alongside temperature.
stop_sequencesoptstring[]Custom strings that halt generation → stop_reason:"stop_sequence".
streamoptbooleantrue → SSE stream. This turns on streaming, not an Accept header. (§6)
metadataoptobjectOnly documented sub-field is user_id — an opaque id/hash for abuse detection. Must contain no PII.
thinkingoptobjectExtended thinking config, e.g. {type:"enabled", budget_tokens:4096}. (§5)
tools / tool_choiceoptarray / objectTool definitions + how to use them. (§4)
service_tieroptenum"auto" | "standard_only" — priority vs standard capacity.
output_configoptobjectReasoning effort (low…max) and structured output (format:{type:"json_schema",…}).

Your real body keys (captured today): model, max_tokens, system, messages, thinking, metadata — exactly the shape above.

3 · The messages array & content blocks

An ordered list of turns. Each turn is { "role": "user" | "assistant", "content": … }. content is either a plain string (shorthand for one text block) or an array of typed blocks. The model reads the whole history and generates the next assistant turn.

Block typeShapeUsed for
text{type,text}Plain text. A string content is exactly this.
image{type,source}source is base64 (media_type+data), a URL, or a Files-API file_id. Put the image before the text.
document{type,source,…}PDF / text / content. citations:{enabled:true} opts into source citations.
tool_use{type,id,name,input}Emitted by the assistant to call a tool. Parse input as JSON, never string-match it.
tool_result{type,tool_use_id,content,is_error?}Sent in the next user turn to return the tool's output. tool_use_id must match.
thinking{type,thinking,signature}Extended-thinking reasoning + an encrypted signature. Echo back unmodified.
redacted_thinking{type,data}Safety-encrypted thinking. Must be passed back untouched, or the next request 400s.

The #1 multi-turn gotcha

The API is stateless — you resend the entire prior conversation every request, including unmodified thinking / tool_use / tool_result blocks. The most common bug: filtering content blocks by type and accidentally dropping redacted_thinking → 400 invalid_request_error. (Resending all that history is also exactly what your proxy's sliding-window trim exists to keep under the cap.)

4 · System prompt & tools

System prompt: a top-level system field — there is no "system" role in messages. String form for simple prompts; array-of-text-blocks form when you want cache_control on parts of it.

Tools: a top-level tools array. Each custom tool is {name, description, input_schema} where input_schema is JSON Schema. The model decides via tool_choice (auto / any / tool / none). The round-trip:

# assistant turn — model asks to call a tool (stop_reason: "tool_use")
{ "role":"assistant", "content":[
  {"type":"tool_use", "id":"toolu_01A…", "name":"get_weather", "input":{"location":"Paris"}} ]}

# YOU run the tool, then answer in the NEXT user turn (tool_result FIRST)
{ "role":"user", "content":[
  {"type":"tool_result", "tool_use_id":"toolu_01A…", "content":"18°C, overcast"} ]}

Gotchas: tool_result must come first in its user turn and immediately follow the tool_use message; tool_use_id must match exactly; forcing a tool (any/tool) suppresses any prose; extended thinking is incompatible with forced tool use. Server tools (web search, code execution) run automatically — you don't send tool_result for those.

5 · Extended thinking, prompt caching & streaming

FeatureHow it's setNotes
Extended thinking"thinking": {type:"enabled", budget_tokens:N}budget_tokens ≥ 1024 and < max_tokens (it counts toward it). Response gains thinking blocks (carry a signature). Newest models default to a "summarized/omitted" display.
Prompt caching"cache_control": {type:"ephemeral", ttl:"5m"|"1h"} on a blockMarks a cache breakpoint (max 4/request). Re-reading a cached prefix is cheap → shows up as cache_read_input_tokens in usage. (This is how your 400k-token sessions stay fast — the prefix is cached.)
Streaming"stream": true in the bodyResponse becomes text/event-stream with named SSE events: message_start → repeated content_block_start/_delta/_stop → message_delta → message_stop (plus ping). Set by the body field, not by Accept.

6 · The dated beta convention

Every anthropic-beta flag is named feature-name-YYYY-MM-DD, where the date is the version of that beta — so you lock onto a stable snapshot, and a future iteration ships under a new date without breaking you. Your captured header, decoded:

anthropic-beta:
  claude-code-20250219            # Claude Code integration
  oauth-2025-04-20                # OAuth (Max) auth
  interleaved-thinking-2025-05-14 # thinking between tool calls
  context-management-2025-06-27   # server-side context tools
  prompt-caching-scope-2026-01-05
  mid-conversation-system-2026-04-07
  extended-cache-ttl-2025-04-11
  context-1m-2025-08-07           # ← 1M window — present ONLY on the "(1M context)" variant

It's the same idea as anthropic-version: 2023-06-01 — that pins the whole API; betas pin individual features.

7 · The twist: model name ≠ the window your client believes

A subtlety we proved on the wire today, worth pinning down because it bit us:

  • On the wire, the model field is always plain claude-opus-4-8 for real messages. The 1M window is requested by the context-1m-2025-08-07 header — never by a [1m] in the model name (that exact string 404s: not_found_error: claude-opus-4-8[1m]).
  • Opus 4.8 is natively 1M, so even without that header it accepts 400k+ tokens (we measured cache_read=418k → 200 OK). So the header is redundant for this model.
  • But Claude Code's client keeps a local window size per model id: it treats claude-opus-4-8 as 200k and claude-opus-4-8[1m] as 1M. That only changes client-side behavior — the /context denominator and the auto-compaction threshold — not the actual API window.

So: "[1m]" is a client label, not an API model. The API truth is "plain model + optional context-1m header"; the client truth is "the label decides what Claude Code thinks your window is." Both matter — at different layers.

8 · The response (the round-trip)

A non-streamed reply mirrors the request's block structure:

{
  "id": "msg_01…",
  "type": "message",
  "role": "assistant",
  "model": "claude-opus-4-8",
  "content": [ {"type":"text", "text":"…"} ],   # same block types as the request
  "stop_reason": "end_turn",                  # end_turn | max_tokens | tool_use | stop_sequence
  "usage": {
    "input_tokens": 4,
    "output_tokens": 27,
    "cache_read_input_tokens": 418221,        # ← cached prefix (your 1M proof)
    "cache_creation_input_tokens": 0
  }
}

To continue the conversation, you append this whole assistant message (text + any tool_use/thinking blocks) onto messages and send the next request. The model is stateless; the array is the memory.

Mental model — the one-liner

The envelope (headers) says who you are, which API version, which beta features. The letter (JSON body) says which model, the message history, and how to think. The model lives in the body; the 1M window is a header (or native); and [1m] is a Claude-Code label, never an API model id.
