Why clicking the claude-toolkit card in Clawd on Desk never focuses it

Post-mortem · 2026-06-08 · diagnosed via multi-agent investigation against Clawd's live focus-debug.log and Win32 window enumeration

TL;DR

All your VS Code project windows — claude-toolkit, dentalchart-backend2, JS010, sugaimprov — are separate top-level windows owned by one shared Code.exe process (PID 10380, 9 windows). To focus a session, Clawd walks up the process tree to that Code.exe and calls Focus(Code.exe.MainWindowHandle). For a multi-window process, Windows returns whichever window is foreground as MainWindowHandle. Each session caches that handle on its first focus and replays it forever after. claude-toolkit's first focus happened while the dental window was up front, so it's pinned to hwnd 198468 (“dentalchart-backend2”) — claude-toolkit's real window 132958 is never targeted, not even once. The code that could pick the right window by title only runs on the Windows-Terminal path, never on the VS Code path. It's not the venv, hooks, proxy, or forking — all four were tested and refuted. A follow-up breadth audit found this hits 4 of 6 live sessions across 4 projects, not just claude-toolkit.

Symptom

Clicking a Clawd session card is supposed to bring that session's terminal window forward. It works for whatever project you're already looking at, but clicking the claude-toolkit card does nothing — you stay on the dental project. Every session runs inside VS Code's integrated terminal, so terminal type is not the difference.

Verified root cause

VS Code multiplexes many workspace windows under a single Code.exe PID. Clawd's focus path for an editor session is:

click card ─► walk process tree up from the session's claude.exe claude.exe ─► powershell.exe ─► Code.exe(28364, MainWindowHandle=0) ─► Code.exe(10380) ◄── owns 9 top-level windows │ ▼ Focus( Code.exe(10380).MainWindowHandle ) │ Windows returns the FOREGROUND window as MainWindowHandle ──► 198468 "dentalchart-backend2" 132958 "claude-toolkit" ← the right one, never chosen

Process.MainWindowHandle on PID 10380 returned 198468 on one probe and 132870 on a later one — it tracks the foreground window. The disambiguation helper that matches a window by title (FindByPidTitles / title candidates, which would correctly find the window titled “claude-toolkit”) is only invoked on the Windows-Terminal branches of the focus helper. The VS Code parent-direct path never calls it, so VS Code sessions are never disambiguated — they just get the shared process's arbitrary MainWindowHandle.

Why do other repos work, then?

Fair question — if Clawd just focuses the foreground window, why doesn't every background card fail? Because each session's target window is decided once and cached. The first time Clawd focuses a session it grabs Code.exe.MainWindowHandle — the window in front at that instant — and pins it in a per-session cache (key agentId|sessionId), replaying it on every later click. The cache only re-resolves if that window closes.

So each session draws a lottery ticket at its first focus:

  • dentalchart's session first resolved while its own window was up front → cached 132870 (its own window) → its card works.
  • claude-toolkit's session first resolved while the dental window was up front → cached 198468 (dentalchart-backend2) → every click brings up dental, never claude-toolkit. The dental window stays open and valid, so the cache never re-resolves — it's stuck wrong.

“Other repos work” is luck, not correctness. The verifier flagged that even dentalchart is “not reliably correct either” — any session can pin to a neighbour's window depending on what happened to be in front at its first focus.

Two failure flavours: (a) wrong live window — the click yanks you to a neighbour's window (claude-toolkit → backend2; faq-1902 → db-backup-tool); two unrelated cards even act as "focus magnets" (hwnd 198468 is the cached target of 3 sessions). (b) dead handle — the cached window was closed, so the click focuses nothing and never self-corrects (the cache only re-resolves on a window-close event, which a dead handle never fires). Three closed windows (1116520, 1509914, 461238) are still being replayed.

Worktree caveat: 3 of the 4 broken sessions are git worktrees of dentalchart-backend2. sugaimprov-1824 and faq-1902 have no VS Code window open at all, so no algorithm could focus "their" window until one exists. claude-toolkit is the cleanest case — a real, open window (132958) that is simply never chosen.

Fixes

1. Give claude-toolkit its own VS Code process  recommended, keeps your workflow

A plain “New Window” won't help — it stays under the same Code.exe PID. Launch claude-toolkit with a separate user-data dir so it gets its own process and a single, unambiguous MainWindowHandle:

code --user-data-dir "C:\Users\user\.vscode-claude-toolkit" "C:\Users\user\Desktop\claude-toolkit"

That instance owns exactly one window, so MainWindowHandle can only be claude-toolkit's window. Click-to-focus then works. Trade-off: that window has its own extension/setting profile.

2. Run claude-toolkit's claude in a standalone Windows Terminal

Clawd's Windows-Terminal focus path captures a real per-window handle and disambiguates by window title, so it targets the correct window. Trade-off: you give up the integrated-terminal workflow for this repo.

3. Upstream fix in Clawd (the real bug)

On the parent-direct path, when the resolved ancestor is Code.exe with multiple top-level windows, enumerate that PID's windows and pick the one whose title contains the session's cwd basename — reusing the FindByPidTitles title-matching Clawd already runs on the Windows-Terminal branch — instead of blindly focusing MainWindowHandle. Location: ...\Clawd on Desk\resources\app.asar (focus helper / makeFocusCmd / buildWindowsTitleCandidates). Invasive (requires repacking the asar); best filed upstream.

Confirm it

Open claude-toolkit via fix #1, click its card, and tail C:\Users\user\AppData\Roaming\clawd-on-desk\focus-debug.log — targetHwnd should now be a handle unique to claude-toolkit, no longer the shared 198468/1116520.
