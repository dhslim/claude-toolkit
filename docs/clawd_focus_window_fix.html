Clawd "Jump to Terminal" -> correct VS Code window

Working checkpoint · 2026-06-09 · machine: Windows 10, ~9 concurrent VS Code windows, Clawd on Desk
One line: Clawd's "Jump to Terminal" focused the wrong VS Code window because every window shares one Code.exe PID. Fixed entirely with editable-file patches + same-length byte edits to the packed app — no asar repack. End state: jumps land on the correct window, all windows supported (not just 5), no visible flicker.

1. The two components involved

This whole thing lives at the seam between two separate pieces of "Clawd":

clawd-desk Clawd on Desk The Electron desktop "pet" app. Detects Claude Code sessions (via hooks), shows session cards, and on Jump to Terminal performs the OS-level window focus. %LOCALAPPDATA%\Programs\Clawd on Desk\

2. The root cause

VS Code multiplexes every project window under a single Code.exe process. Clawd's desktop-side focus walks the Claude process tree up to that Code.exe and raises its MainWindowHandle — but Windows returns whichever of the 9 windows is frontmost, so the focus lands on the wrong window. A breadth audit found 4 of 6 live sessions resolving to the wrong window.

The Clawd Terminal Focus extension could fix it — the extension instance that owns the right terminal is, by definition, already running inside the correct window — but stock, it only calls terminal.show() (right tab, still wrong window).

3. The focus flow (and where the flicker came from)

CLICK "Jump to Terminal" | | clawd-desk focusTerminalWindow(request) | +--> STAGE 1 requestWindowsFocus() [fires immediately] | persistent PowerShell -> [WinFocus]::Focus(MainWindowHandle) | => raises the WRONG window (this is "B") | +--> STAGE 2 scheduleTerminalTabFocus() [setTimeout, was 800ms] POST /focus-tab {pids} to ports 23456..N | v extension in the matching window terminal.show() => right tab raiseOwnWindow() => raises the CORRECT window (this is "C") Perceived: A (current) -> B (wrong, flash) -> C (correct) Goal: A (current) ----------------------> C (correct)

The flicker existed because Stage 1 paints the wrong window the instant you click, and Stage 2 can only correct it after a delay. The final fix deletes Stage 1's raise entirely, so B never happens.

4. The fix, in the order it evolved

4a. Teach the extension to raise its own window extension

Added raiseOwnWindow() to focusTerminalByPids: after terminal.show(), the extension reads its own workspace folder basename (e.g. claude-toolkit), finds the visible Code.exe window whose title contains that name, and raises it with the AttachThreadInput + SetForegroundWindow trick (defeats Windows' foreground lock). Verified each of the 9 windows has a unique folder name in its title.

4b. Make it actually run, then make it instant (v1 -> v4) extension

VerChangeWhy
v1spawn powershell.exe, AttachThreadInput raisefirst cut; window didn't move
v2/v3full path to powershell.exe + debug log to %TEMP%\clawd-focus-debug.logthe ext-host has a stripped PATH; logging proved the raise WAS running but a fresh spawn each click was slow/variable
v4persistent warm PowerShell helper: compile the Win32 focus type once, keep it alive, feed it the window name per click via stdindrops each raise from ~350ms (spawn+compile) to ~20ms, and makes it consistent

4c. Remove the 5-window limit extension + clawd-desk

Both sides hardcoded 5 ports (23456-23460), one per window — so only 5 of ~9 windows ever got a focus listener. Raised to 44 (ports 23456-23499):

  • extension PORT_RANGE = 5 -> 44 (how many ports the extension will try to bind).
  • clawd-desk the broadcast loop upper bound port <= 23460 -> 23499 (which ports the app POSTs to). Same-length byte edit (both 5 digits), so no repack.

Why 44 and not more? The packed edit must keep the byte length identical (so the asar header offsets stay valid). 23460 -> 23499 keeps it 5 digits and inside the original 234xx block. 23456..23499 = 44 windows. Could go to 23999 (544) just as safely; 44 is already overkill.

4d. Cut the delay clawd-desk

Stage 2's setTimeout(..., 800) was 800ms. Byte-edited 800 -> 200 (same 3 digits). Safe for the race because our warm-helper raise is still bounded below by spawn latency, so it always lands after Stage 1.

4e. Delete Stage 1 entirely (the flicker killer) clawd-desk

The clean fix for the flicker: stop Clawd from ever painting the wrong window. Inside the packed WinFocus C# helper:

void Focus(IntPtr hWnd) {
    if (hWnd == IntPtr.Zero) return;          // guard
    if (IsIconic(hWnd)) ShowWindow(hWnd, 9);  // restore if minimized
    keybd_event(0x12, ...); keybd_event(0x12, ...);  // ALT-trick
    SetForegroundWindow(hWnd);                 // <- the wrong-window raise
}

Flipping the guard's == to != (one byte, = -> !) makes the method return immediately for any real window — the whole body (restore + ALT + SetForegroundWindow) becomes a no-op. Clawd still runs its bookkeeping and still fires Stage 2, but it paints nothing. Result: A -> C, no B, no flicker.

An identical guard exists in another method (GetWindowClass-style, returns ""); it was left untouched by anchoring the edit to the unique SetForegroundWindow(hWnd) call.

6. Exact byte recipe (for reproduction)

All three app.asar edits are same-length, in-place byte overwrites (the asar is a header of file offsets/sizes + concatenated bodies; keeping total length identical keeps every offset valid, so no repack). Target file: ...\Clawd on Desk\resources\app.asar. Backup kept as app.asar.clawd-orig.

1) broadcast range   find  "port <= 23460"   set  "port <= 23499"
2) focus delay        in the /focus-tab setTimeout, "}, 800)" -> "}, 200)"
3) stage-1 neuter     the WinFocus Focus guard preceding the unique
                      "SetForegroundWindow(hWnd)" call:
                      "hWnd == IntPtr.Zero) return"  ->  "hWnd != IntPtr.Zero) return"

Extension (plain text edit, both copies):
   const PORT_RANGE = 5   ->   const PORT_RANGE = 44
   + the raiseOwnWindow()/warm-helper block (see patches/clawd-focus/extension.patched.js)

7. Reapply & revert

patches\clawd-focus\apply.ps1 is the one-command restore for both halves: it redeploys the patched extension.js to both copies and re-applies the three app.asar byte edits (each anchored to unique context; it warns instead of writing if Clawd's code changed shape). apply.ps1 -Revert restores stock everywhere (and refuses to restore a stale asar backup over a freshly-updated asar). After applying: restart the Clawd app (asar) + reload VS Code windows (extension).

8. Caveats / not covered

  • SSH-remote windows ([SSH: host]) are not handled: the extension is a workspace extension that would run on the remote host (Linux, no Win32 raise), the terminal PIDs are remote, and the local-PID matching doesn't apply. Would need a separate title-based path.
  • Git worktrees with no open window have no window to raise — unavoidable.
  • Side effect of 4e: Clawd's built-in focus is now off for all editors, not just VS Code. Fine for a VS-Code-only workflow; the extension handles VS Code.
  • Update fragility: a Clawd update reverts the app.asar edits and re-deploys the stock extension. One command restores everything: apply.ps1 (covers extension + all three asar edits), then restart Clawd + reload windows.
  • asar integrity: confirmed Clawd does not verify app.asar integrity (it relaunched fine after every byte edit), which is what makes the in-place edits viable.

9. Status

Working checkpoint: jumps land on the correct window across all windows, the 5-window cap is gone (44), focus is snappy (~200ms), and the wrong-window flicker is eliminated — all via editable-file patches and same-length byte edits, no asar repack.
