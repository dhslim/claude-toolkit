Bug A: should the proxy short-circuit the [1m] quota probe?

A focused look at one of the two bugs covered in today's broader post-mortem: Claude Code's malformed [1m] quota probe, the four options we considered for the proxy, and why we shipped the conservative one even though the aggressive one is fifteen lines away.

2026-05-22 KST · supplement to 2026-05-22_context_limit_investigation.html · related: claude_proxy_explainer.html

TL;DR

Claude Code 2.1.148 fires a malformed quota probe ("claude-opus-4-7[1m]" in the model id where [1m] should be a header); Anthropic 4xxs it; CC misreads the 4xx as "Context limit reached." We considered four proxy responses — do nothing, rewrite-and-pass, synthetic short-circuit, file upstream — and shipped rewrite-and-pass while deferring the synthetic. The synthetic stays deferred not because it's wrong but because it crosses the proxy from "honest broker" into "opinionated mock," and the alternative is cosmetic friction, not real failure.

1 · The probe and its purpose

On certain trigger moments — new session, near-context-low events, possibly others — Claude Code 2.1.148 fires a tiny request whose body looks like this: 

{
  "model": "claude-opus-4-7[1m]",
  "max_tokens": 1,
  "messages": [
    {"role": "user", "content": "quota"}
  ]
}

The [1m] suffix on the model id is malformed. Anthropic's 1M-context beta is opted into via a header (anthropic-beta: context-1m-2025-08-07), not by mangling the model id. Anthropic responds with a 4xx (we've seen both 404 and 429). Claude Code interprets any first-attempt 4xx on a turn as "context exhausted" and shows the alarming red banner: 

  └ Context limit reached · /clear to continue

~10 s later CC silently retries the real request (without the bogus suffix); that one succeeds and the session continues. So the user-visible effect is a false-alarm banner that fires roughly ~20 times per day on this machine and resolves itself before they can act on it.

The likely purpose theory, not confirmed

Why does CC send this probe at all? The cleanest hypothesis: it's an entitlement check. CC needs to decide whether to format the upcoming real turn for 200K context (default) or for 1M context (beta). It doesn't know offline which entitlement the account has — Pro caps at 200K, Max at 1M, API plans vary. So before committing the real turn's shape, it fires the cheapest possible probe asking "would a [1m] request be accepted?"

  • If Anthropic returns 200: account is 1M-entitled, format the real turn for 1M.
  • If Anthropic returns 4xx: fall back to 200K formatting.

The [1m] ending up in the model id rather than the header is almost certainly a regression in 2.1.148 — someone refactored the probe path and spliced the marker into the wrong field. The fallback-on-4xx logic still works (the real call goes through with the bare id), but the user sees the false-alarm banner every time the probe fails.

Supporting evidence — public GitHub issues

None of these are exactly this bug, but together they corroborate that [1m] handling regressed around this version and that 1M / 200K confusion is rampant:

2 · The four options

Option 1

Do nothing

Status quo before today. Probe goes straight to Anthropic; 4xx fires banner; CC self-recovers.

Pros: zero proxy code.

Cons: ~20 false-alarm banners/day; alarming for new users; no forensics.

SUPERSEDED · 0 LOC

Option 2 — current

Rewrite-and-pass

Proxy detects [1m] in model id, strips it, attaches the anthropic-beta: context-1m-2025-08-07 header, dumps the body for forensics, forwards to Anthropic.

Pros: honest broker preserved — Anthropic still decides; forensics dump lets us tell Bug A from Bug B if banner recurs.

Cons: Anthropic still 4xxs the rewritten request (the quota path has its own validation/rate-limit), so the banner still fires. User-visible problem not solved.

SHIPPED · ~30 LOC · commit b2e32a4

Option 3

Synthetic short-circuit

Proxy detects the probe fingerprint (max_tokens==1 AND content=="quota") and returns a synthetic 200 directly — never forwards to Anthropic.

Pros: banner stops firing entirely; ~15 LOC; cheap rollback.

Cons: proxy becomes "opinionated mock"; account-coupled (fails louder on a non-1M key); schema-drift risk.

crosses the broker/mock line

DEFERRED · ~15 LOC · documented, not shipped

Option 4

File upstream

Open an Anthropic GitHub issue with the captured probe body, rewritten body, response, and CC version. Get it fixed at the source.

Pros: highest leverage — fixes it for every CC user; renders Options 2 & 3 dead code once shipped.

Cons: timeline uncertain (weeks–months); doesn't help today's pain.

3 · The dilemma: honest broker vs. opinionated mock

The proxy was designed as an honest broker. It sits between CC and Anthropic, fixes a few mechanical issues (sliding-window trim, malformed-field rewrites), and otherwise lets Anthropic decide. Every request that goes in comes out modified-but-equivalent on the other side; every response that comes back is genuine.

The synthetic short-circuit moves the proxy partway into a different category. It becomes a mock: it answers a known-shaped question from local knowledge instead of forwarding. The dilemma isn't that mocks are inherently bad — they're how most test infrastructure works. It's that the proxy did not start life as a mock, and once one synthetic response lives in the codebase, the next "we know what CC wants here, let's just answer" temptation is easier to take.

Caching layer · transparent

Re-asks when uncertain. Forwards genuinely.

The proxy as built. Rewriting [1m] into a header still asks Anthropic the question. The answer that flows back to CC is Anthropic's answer, whatever it is.

If something behaves oddly, "look at the upstream response" is a legitimate first step. Logs are causally linked to a real round trip.

Mock service · opinionated

Answers from local knowledge. Skips the upstream.

What Option 3 would make part of the proxy. The 200 we hand CC is fabricated by us; Anthropic never saw the question.

If something behaves oddly, the proxy log shows a "200" that nobody upstream signed off on. Causal chain has a gap.

Why this matters in practice — four reasons

  1. Portability. The synthetic encodes the assumption "this machine's API key has 1M entitlement." Move the proxy to another machine whose key doesn't, and CC sees a fabricated "yes" — then the real follow-up turn (formatted for 1M) lands a 400 from Anthropic. That failure is louder and stranger than the banner the synthetic was meant to suppress.
  2. Debuggability. When something misbehaves three weeks from now and we read proxy.log, a synthetic 200 looks identical to a real upstream 200. We'd have to remember "oh, that endpoint is mocked" before we even start diagnosing. Every additional synthetic erodes the "the log tells you what happened" property.
  3. Surface area / slippery slope. The proxy currently has one clean rule — "be Anthropic's pass-through with a couple of small repairs." Adding synthetic responses opens a category: every future request shape we recognise becomes a candidate for short-circuiting. There's no obvious stopping rule once we start.
  4. Failure modes shift, not shrink. The current failure (banner) is loud and visible — the user sees a false alarm and an explicit message. A bad synthetic causes subtler failures (CC misbehaves quietly without an obvious culprit). Loud failures are easier to triage than quiet ones, even if they're more annoying day-to-day.

4 · Decision: ship Option 2, file Option 4, defer Option 3

The reasoning, in order of weight:

  1. Bug A is cosmetic; Bug B was real. The banner fires, CC retries, work continues. The actual workflow-blocking issue today was Bug B (over-cap 400s on huge sessions) — which got a real fix. Bug A is UI cry-wolf, not a stuck session.
  2. Honest-broker invariant preserved. Rewrite-and-pass cleans up a malformed field. It doesn't fabricate answers. Anthropic still decides.
  3. Forensics-first. The proxy_1m_dump.json in Option 2 means that if the banner reappears tomorrow we can tell instantly whether it's Bug A recurring or something new. Option 3 would silently suppress the banner whether the underlying probe was healthy or sick — we'd lose that signal.
  4. Option 4 is higher-leverage. A filed Anthropic-side bug fixes this for every CC user. Local synthetic patching is per-machine. Once Option 4 ships, both Options 2 and 3 become dead code.
  5. Portability matters. This proxy might run on other machines or accounts in the future. Option 3 has account-specific safety baked in.
  6. Cheap to revisit. Option 3 is fifteen lines and a proxy restart away. Deferring it is not the same as foreclosing it.
Be explicit: defensible, not obviously right
This is "a defensible choice," not "the only defensible choice." A different engineer with the same evidence could reasonably ship Option 3 today, and the next section catalogues why.

5 · Counter-arguments

The honest pushbacks against the chosen direction:

  1. Rollback really is cheap. Fifteen lines, one git revert, one proxy restart. The "philosophical dilemma" framing is partly a justification for caution. We could have shipped Option 3 today and reverted in 30 seconds if it broke anything.
  2. "Honest broker" is a value, not a law. Plenty of production proxies happily synthesise responses for known-malformed inputs — particularly when the upstream itself is buggy. The line we drew between "rewrite a field" and "answer the question" is somewhat arbitrary. Both are interventions; the difference is degree.
  3. ~20 banners/day is real friction. Especially for new users who don't know the banner is lying. "Cosmetic" is doing a lot of work in the decision rationale; a UI element that screams "your session is dead" twenty times a day is not pure cosmetics.

6 · For the record: what Option 3 would look like

If we ever ship Option 3, this is the shape we'd hand back to CC:

{
  "id": "msg_synth_quota_<uuid>",
  "type": "message",
  "role": "assistant",
  "model": "claude-opus-4-7",
  "content": [
    {"type": "text", "text": "ok"}
  ],
  "stop_reason": "end_turn",
  "stop_sequence": null,
  "usage": {
    "input_tokens": 1,
    "output_tokens": 1
  }
}

The detection fingerprint, paraphrased:

is_quota_probe = (
    body.get("max_tokens") == 1
    and len(body.get("messages", [])) == 1
    and body["messages"][0].get("role") == "user"
    and body["messages"][0].get("content") == "quota"
)

Tight enough that a real user request reading "quota" with max_tokens=1 would also match — which is an acceptable false-positive surface (such a request would itself be malformed and produce a useless response anyway).

7 · Revisit conditions

When would we reopen Option 3?

  • Anthropic issue languishes >3 months. If Option 4 doesn't move, the cost-benefit shifts toward local patching.
  • Onboarding friction becomes a real complaint. If anyone other than current-me ends up using this machine and the banner causes confusion or lost work, the cosmetic argument weakens.
  • The proxy gains other synthetic responses anyway. If a future change makes synthetic responses an established pattern in this codebase (e.g. local handling of some other malformed CC request shape), the broker-invariant argument is already gone — Option 3 then costs nothing extra philosophically.
  • CC's behaviour around the probe changes badly. If a future CC version stops the silent retry and the banner becomes blocking, "cosmetic" is no longer accurate and Option 3 becomes urgent.
