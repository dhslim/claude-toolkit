How claude -c Resolves the Model

Why a resumed session comes back on whatever model it last answered with — proven by reverse-engineering the Claude Code binary — and why the proxy's [1m] rewrite turns out to be vestigial.

1 · Summary & the headline finding

claude -c / --continue picks the resumed model by reading the message.model field of the last genuine type:"assistant" line in the resumed transcript JSONL — not settings.json, not ~/.claude.json, not an env var, and not the floating default. The model you get back is the one that last produced a reply in that session.

The full headline, end to end:

claude -c resolves the resumed model from the last assistant message's message.model in the transcript JSONL (proven by reverse-engineering the Claude Code 2.1.193 binary, and independently reproduced on the local 2.1.195 build) — not from settings/env/default. The proxy's [1m] → header rewrite is vestigial on current Claude Code: real messages never invoke it and the throwaway startup probe fails harmlessly. And [1m] maps to the anthropic-beta: context-1m-2025-08-07 header — which is redundant for Opus 4.8 because that model carries 1M natively (bare claude-opus-4-8 requests were observed accepting up to ~699k tokens at HTTP 200).

2 · The question & why it matters

The symptom that started this: a session reopened with claude -c kept coming back on the "wrong" model. The label in the terminal would read "Opus 4.8" on a resume but "Opus 4.8 (1M context)" on a fresh launch — and at one point a session whose settings.json said "sonnet" resumed as Haiku. Three actors were suspects:

the agent · decides the model

Claude Code (CC)

Turns the conversation into an HTTP request and chooses the model string. -c is its --continue flag: resume the last conversation in the current directory.

your code · localhost

claude_proxy.py — "Sluice" :9999

Every CC request flows through it. It rewrites a [1m] model suffix into a header and trims oversized context. It does not touch model resolution.

on disk · the transcript

The session JSONL

~/.claude/projects/<slug>/<sessionId>.jsonl — one line per message. Each assistant line carries a message.model. This is where -c reads the model from.

It mattered because the user feared the 1M window was silently collapsing back to 200k on every resume. The investigation had to separate three independent things that were being conflated: (a) which model a resume restores, (b) what the proxy's [1m] rewrite actually does, and (c) how the 1M window is really switched on. They turn out to have different answers — and only one of them is even a real problem (and not for Opus 4.8).

3 · How claude -c resolves the model confirmed · binary RE

The decision is made entirely inside Claude Code, from the transcript on disk. No setting, env var, or proxy is consulted on the default resume path.

The three functions that do it

The mechanism lives in three compiled functions plus a gate. Bun-minification renames them per build, so the symbols differ between versions — but the string literals and control flow are identical. Below, the 2.1.193 names (from the Windows binary RE) are paired with the 2.1.195 names (independently reproduced on the local Mac build):

The resume override — the heart of it

After the transcript is deserialized, this scans from the tail and returns the model of the last real assistant line (skipping isMeta lines and the synthetic-model sentinel, bound literally as <synthetic>):

// Sdc (2.1.193) / Gbc (2.1.195) — the resume override
for(let s=e.length-1; s>=0; s--){
  let i=e[s];
  if(i?.type!=="assistant" || i.isMeta || i.message.model===FC) continue;  // FC = "<synthetic>" sentinel
  let a=i.message.model;
  ...
  return {kind:"ok", model:a};                          // <- last API-call model
}

The wrapper applies that into session state — but only if the gate allows:

// mGo (2.1.193) / MKo (2.1.195) — the gate
function mGo(){ return Boolean(My()!==void 0 || process.env.ANTHROPIC_MODEL || !Xu()) }  // skip restore if --model / env set

// nKe (2.1.193) / CYe (2.1.195) — the apply
let x=nKe(S,_.mainLoopModel, warn);
let k=x ? rKe(S,x,fork) : void 0;
if(k) n(X=>({...X, mainLoopModel:k}));   // session model := last assistant message's model

A telemetry event named tengu_resume_model_restore is emitted right here — this is a deliberate "resume model restore" feature, not an accident. (In 2.1.195 the literal tengu_resume_model_restore appears 6 times and is emitted inside the apply function.)

Why a send is required to "commit" a model

Only an actual API call appends an assistant line carrying a model field to the JSONL. /model alone writes settings.json .model and sets an in-memory mainLoopModelOverride — but it produces no transcript line. On a fresh -c, the in-memory override is gone, so the resume override walks the transcript and picks the last model that produced a response.

That is exactly why settings.json said sonnet yet -c came back Haiku: the last assistant line in that transcript was Haiku, and the apply overrode the settings baseline.

⚠ Precision caveat — the gate

"NOT an env var" is only true absent an explicit override. The gate (mGo/MKo) deliberately skips the transcript restore when --model or ANTHROPIC_MODEL is present — so those can override the transcript model. The accurate statement is: the default resume path uses the transcript model rather than settings/floating-default; a per-launch --model (or ANTHROPIC_MODEL) beats it. The baseline resolver itself still reads settings.json / ANTHROPIC_MODEL — it is the resume override that wins on a plain -c.

The [1m] / alias handling

The JSONL stores the bare API id (claude-opus-4-8). On restore, the override re-appends the tag when the configured model carries it:

return {kind:"ok", model:a+"[1m]"};   // re-append the 1M tag

Aliases are parsed by parseUserSpecifiedModel, stripped to API form by normalizeModelStringForAPI / strip1mTag. The string literals parseUserSpecifiedModel, normalizeModelStringForAPI, strip1mTag, and <synthetic> all exist verbatim in the 2.1.195 build. (Minor: the digest mapped "default" resolution to ry(); in 2.1.195 ry() is the --model override getter and the floating-default fallback is a different function — a cross-version mangled-name imprecision that doesn't change the behavior.)

4 · The proxy [1m] rewrite — and why it's vestigial

Separate from model resolution: the proxy ("Sluice", claude_proxy.py on :9999) rewrites a [1m] model suffix into a header. Here is exactly what it touches, and the finding that it is no longer load-bearing.

The function — the only place the proxy touches the model field confirmed

_normalize_cc_1m_suffix() (claude_proxy.py L297–325) is the only code in the whole proxy that mutates body["model"] or adds context-1m to the header. Verbatim:

def _normalize_cc_1m_suffix(body: dict, headers_dict: dict) -> bool:
    model = body.get("model", "")
    if not (isinstance(model, str) and model.endswith("[1m]")):
        return False
    body["model"] = model[: -len("[1m]")]
    ...
    if "context-1m-2025-08-07" not in betas:
        betas.append("context-1m-2025-08-07")
    headers_dict["anthropic-beta"] = ",".join(betas)
    return True

Its docstring documents the original rationale and notably predates this investigation — it still references CC 2.1.145 and model claude-opus-4-7:

"""Strip CC 2.1.145's malformed [1m] suffix on model id; move to anthropic-beta.

Claude Code 2.1.145 sends model="claude-opus-4-7[1m]" instead of using the
proper anthropic-beta: context-1m-2025-08-07 header. Anthropic returns 404
because that model id doesn't exist, and CC misinterprets the 404 as
"Context limit reached / /clear to continue" on the FIRST prompt of a
session.
"""

⚠ The log line is stale

The call site (L1017–1030, guarded by a plain if body:) hard-codes its log text to the 4-7 era regardless of the actual model:

[proxy] 🔧 rewrote model=claude-opus-4-7[1m] → claude-opus-4-7 + anthropic-beta: context-1m-2025-08-07

The function itself is model-agnostic (it strips any trailing [1m]), so it still works on claude-opus-4-8[1m] — but every 🔧 rewrote line misreports the family as 4-7. A skeptic grepping the log for the model would be misled.

The session-startup quota probe corrected from digest

The [1m] suffix only ever appears on one request: a tiny probe Claude Code fires once per session launch (not per-message, not on a timer). It's a cheap quota/rate-limit check — CC wants the anthropic-ratelimit-* response headers, not the answer. Captured verbatim on the wire (proxy_1m_dump.json, 2026-06-27 16:29 KST), this is the request as the proxy forwarded it (the [1m] already stripped):

# User-Agent: claude-cli/2.1.195 (external, cli)
# POST https://api.anthropic.com/v1/messages?beta=true   body_size: 324
{
  "model": "claude-opus-4-8",            # CC sent "...4-8[1m]"; proxy stripped it
  "max_tokens": 1,
  "messages": [{ "role": "user", "content": "quota" }],
  "metadata": { "user_id": "{\"device_id\":...,\"account_uuid\":...,\"session_id\":...}" }
}

Corrections applied from on-disk verification of the digest's earlier figures:

  • Body is 324 bytes on the wire (post-rewrite), not the ~317 the digest repeated — the 4-byte difference is the stripped [1m].
  • Live User-Agent is claude-cli/2.1.195 (the Windows box was 2.1.193) — version is per-machine.
  • metadata.user_id is a nested JSON blob (device_id / account_uuid / session_id), not a bare redacted string.
  • The proxy does not merely forward the probe: because CC emits model=claude-opus-4-8[1m], _normalize_cc_1m_suffix strips the [1m] and ensures context-1m-2025-08-07 is in the header before forwarding. CC builds the request; the proxy mutates it.

A classic two-code-paths-one-got-fixed inconsistency — on CC's side. In proxy.log, real messages (including 1,200+ POSTs over 1 MB) go out as bare claude-opus-4-8 and are never preceded by a 🔧 rewrote line; the rewrite fires only on the tiny probes (≈31 rewrite events over two weeks).

The "vestigial" finding conclusion confirmed; mechanism corrected

The investigation tested whether the rewrite is load-bearing:

"Context limit reached / /clear"
→ session breaks on first prompt
→ the rewrite is essential

Hypothesis B — vestigial ✓

CC shrugs off the failure
→ boots and replies normally
→ the rewrite isn't doing
  anything load-bearing

On the Windows box the test was staged behind a flag-file toggle so the [1m] probe could pass through untouched:

# Before:  always run the rewrite
if body:

# Experiment: skip it when the flag file exists
if body and not _skip_1m_rewrite:     # _EXPERIMENT_skip_1m_rewrite.flag

Across 3 fresh sessions the raw claude-opus-4-8[1m] went out, Anthropic returned 404 not_found_error, and every session booted and replied normally — Hypothesis B. (Wire log: 15:52:05 [1m] out → 15:52:06 404; 15:53:54 [1m] out → 15:53:58 404.)

⚠ What current local data shows instead (corrections)

  • The flag experiment is not in the current Mac repo — there is no _EXPERIMENT_skip_1m_rewrite.flag and no _skip_1m_rewrite logic. The live guard is a plain if body: (L1018). The experiment was reverted; the snippet above is quoted as it ran on Windows, not as code that runs today.
  • The current failure mode is not a model-not-found 404. The probe is rewritten to a valid bare model first, so it returns 429 rate_limit_error (or 401 auth) — e.g. the captured dump shows status 429. The raw-[1m]→404 direct-replay result is from the Windows session and is not reproducible from this repo.
  • Every 404 in the local proxy.log is a response to CC's HEAD / health check (empty body, ttfb=-1ms), not a probe response.

✓ The conclusion stands — and is supported more directly by local data

The _normalize_cc_1m_suffix rewrite is not load-bearing on current Claude Code: real messages already go out as bare claude-opus-4-8 with the context-1m header and succeed at HTTP 200 (cache_read observed up to ~699k tokens), so [1m] only ever rides the throwaway probe — and a failing probe doesn't break the session. Only ~31 rewrite events exist against thousands of successful real requests. The dramatic "Context limit reached" severity in the docstring, if it was ever real, belongs to the older CC 2.1.145 the shim was written for — it does not reproduce on 2.1.193+/2.1.195.

5 · The 1M-context mechanism confirmed

The 1M context window is requested via the anthropic-beta: context-1m-2025-08-07 header (or, for the newest models, natively) — never via a [1m] model-name suffix. claude-opus-4-8[1m] is a CC-internal label; the API has no such model id (which is why the raw suffix 404s).

KnobWhereEffect
modelbodyPicks the brain (claude-opus-4-8). Not the window size.
anthropic-betaheadercontext-1m-2025-08-07 is what flips 200k → 1M for models that need it.

The 2025-08-07 is the version date of the context-1m beta. Anthropic dates beta flags so clients lock onto a stable feature version; a later iteration ships a new date and the old one keeps old behavior until retired. externally confirmed (the public "1M tokens" announcement followed ~Aug 12, 2025; this dated flag was later retired ~2026-04-30 for Sonnet 4/4.5 as 1M went GA on the newer generation).

Opus 4.8 carries 1M natively — so the suffix and header are both redundant for it

Ground-truth on the wire: bare claude-opus-4-8 requests succeeded at HTTP 200 with cache_read up to ~699k tokens — far above any 200k ceiling. So the "1M reverting to 200k" the user feared was never real for Opus 4.8; only a cosmetic label flickered ("Opus 4.8" vs "Opus 4.8 (1M context)"). The 200k figure was just Claude Code's local /context meter mis-believing the bare id is a 200k model — CC's client accounting hadn't caught up to Opus 4.8 being natively 1M.

But for a model that genuinely needs the header for 1M (older Opus, Sonnet 4), this same -c behavior — restoring the bare model and not always re-appending the 1M tag/beta — would silently cut a resumed session back to 200k. That would be a real bug in those cases; it just isn't one for Opus 4.8.

Caveats from verification: the specific claim that a 418k-token request carried no context-1m header isn't strictly isolable from the local log (the proxy doesn't log full headers on successful requests, and CC includes context-1m in its own beta list for real messages). What's proven is that the real window is far above 200k for bare claude-opus-4-8 — not strictly "native, zero header." The "/context shows 200k" half is CC client accounting, outside the proxy.

6 · Implications & takeaways

  1. A resume restores the model that last answered. -c reads message.model from the last real assistant line. To change what a resume restores, you must send a message on the desired model in that session — picking it in /model without sending does nothing for -c.
  2. settings.json .model is only the baseline. It seeds a fresh launch; the resume override beats it. That's why settings saying sonnet didn't stop -c from returning Haiku.
  3. The only lever that forces a model on a resume is a per-launch override. --model claude-opus-4-8[1m] (or ANTHROPIC_MODEL) trips the gate and skips the transcript restore. unverified — see open questions: this was teed up but not confirmed in-window.
  4. This is stock Claude Code, not your toolkit. Reproduced on a no-proxy, different-version, different-OS Ubuntu box. The proxy plays no part in model resolution.
  5. The proxy's [1m] rewrite is vestigial on current CC. Real messages never use it; the throwaway probe fails harmlessly. Worth keeping for older-client safety, but it is not what makes 1M work today.
  6. 1M lives in the header, and Opus 4.8 has it natively. The window never actually dropped to 200k for Opus 4.8 — only the label and CC's local meter did.

7 · Open questions

Carried forward from the investigation's own gap list — stated plainly so this doc doesn't overclaim.

  • Does a per-launch --model claude-opus-4-8[1m] actually beat -c and survive a resume? Not confirmed in-window — the automated claude -c -p print-mode test hung (as did setting model in settings.local.json). Interactive verification was left to run by hand. The binary's gate logic predicts it should work, but it wasn't observed end to end.
  • The 404 severity in the docstring is unverified and likely overstated. "CC misinterprets the 404 as Context limit reached / /clear on the FIRST prompt" was never directly observed and the experiment contradicted it on current CC. It may have been true only on the CC 2.1.145 the shim was written for.
  • Who runs claude -c on restart is inferred, not measured. The "computer restart → sessions auto-relaunched with claude -c" chain rests on seeing claude.exe -c in the process tree; the exact restore-orchestrator (assumed window/IDE restore) is a well-supported guess.
  • The exact seed test artifact is not in the data. "settings said sonnet yet -c resumed as Haiku" is consistent with the confirmed mechanism (transcripts on disk do contain claude-haiku-4-5 lines) but the specific session id / screenshot of that run isn't captured here.
  • Header-level proxy logging was never permanently added. Early claims that big bare-4.8 sessions send the context-1m header themselves were inferences, later turned into ground truth by a pcap A/B; the proxy log still records model strings, not full headers, on successful requests.
