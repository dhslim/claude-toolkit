claude-chat-search — Architecture ✓ STACK LOCKED · 2026-06-30

A private, always-available, single-user web service to search your entire Claude history — hybrid lexical + semantic, on plain Postgres, served serverless.

One line: Neon + Postgres-native hybrid search + bge-m3-via-DeepInfra + a Vercel serverless app, behind a Cloudflare passkey.

Host decision: Vercel, not EC2. This is a request/response tool (open → search → done), so serverless fits — scales to zero, ~$0, no box to babysit. EC2 stays a future option if it ever grows into 24/7 autonomous work; migrating is cheap because the data lives in Neon, not on the host.

How a search flows

any device, any network │ https://chat.<yourdomain> ▼ ┌──────────────────────────────────┐ │ Cloudflare Access (passkey) │ public URL, but only YOU pass └───────────────┬──────────────────┘ │ proxied (+ CF-Access JWT in header) ▼ ┌──────────────────────────────────────────────┐ │ Vercel serverless function │ │ • serves the search page │ │ • /api/search : verify CF-JWT → embed → query │ │ │ │ │ │ embed query│ SQL │ │ └────────────┼─────────────────────┼───────────────────────┘ ▼ ▼ ┌──────────────────┐ ┌──────────────────────────┐ │ DeepInfra bge-m3 │ │ Neon Postgres claude_chat │ │ (only the QUERY TEXT │ │ pgvector + tsvector + RRF │ │ leaves — never chats) │ │ (state lives HERE, not Vercel) │ └──────────────────┘ └──────────────────────────┘

Your chats never leave — they're already embedded and sit in Neon. The only thing that exits is the search phrase you type, sent once to DeepInfra for its 1024-dim vector. The Vercel function is stateless — it holds nothing precious, which is exactly why it's swappable later.

Why this stack (derived, not picked)

  • Search = plain Postgres, not ES/Lakebase. Single user → a bounded ceiling that never reaches where heavyweight search earns its keep. At 16k rows, brute-force pgvector is exact; an ANN index would be a downgrade. Revisit only at ~150k–300k msgs.
  • Embedding = DeepInfra, not on-box. bge-m3's ~2.3 GB RAM was the entire cost driver. Offloading the query embed (~fractions of a cent each) lets the host be a free serverless function.
  • Host = Vercel, not EC2. A search is request/response — it only runs when you open it. Serverless scales to zero, costs ~$0, and needs zero maintenance (no SSH, patches, or security groups). EC2's versatility is wasted here — reserve it for if this grows into 24/7 autonomous work.
  • Low lock-in by design. State = Neon + DeepInfra (both external). Vercel is dumb stateless compute. Outgrow it → re-wrap the entry point onto EC2/a container, point at the same Neon + DeepInfra. ~half a day, not a rebuild.

Gotchas to honor when building

  • Embedding must match: DeepInfra must return bge-m3 at 1024-dim, L2-normalized (cosine) — same as the corpus. Any other model/dim → cosine scores are meaningless.
  • Lexical config: the query side must use plainto_tsquery('simple', q) — your body_tsv is the 'simple' config (KO/EN-safe). 'english' mis-tokenizes + skips the index.
  • Vercel Hobby URLs are public: the raw *.vercel.app URL bypasses Cloudflare. So the function must verify the Cloudflare-Access JWT (or a shared secret) and reject requests without it — otherwise "private" isn't.
  • Stay portable: keep state in Neon + DeepInfra; avoid Vercel's proprietary data products (Vercel KV/Postgres/Edge Config). Vercel = runtime only → the EC2 exit stays a half-day, not a rebuild.
  • Secrets server-side: DATABASE_URL + the DeepInfra key live in Vercel env vars, never shipped to the browser.
