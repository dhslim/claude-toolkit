quiz_data.py — filter messages in the DB, not on the client

claude-toolkit · 2026-06-21 · daily-quiz data fetcher
One line: The daily-quiz source fetcher filtered by session start time, so long-running sessions that were active yesterday but started days ago were silently excluded — feeding the quiz generator 15 of 72 real messages and forcing a slow ~12 min client-side fallback. Fix: match on each message's timestamp inside a MongoDB aggregation — no session_started_at gate, and only the messages we need cross the wire.

1. What this script does

quiz_data.py feeds the daily quiz: it pulls yesterday's conversation messages from the shared MongoDB sessions collection so the quiz-generator agent can write questions grounded in real work. Every session document holds a messages array; each message has its own role, content, and timestamp.

2. The bug — a session-level gate on message-level data

Sessions are long-lived. One Claude Code session can run for weeks (this very claude-toolkit session started 2026-05-24). What matters for "yesterday's activity" is the timestamp of each message, not when its session began. The old code conflated the two:

three_days_ago = now - timedelta(days=3)
sessions = db['sessions'].find({
    'session_started_at': {'$gte': three_days_ago, '$lte': end}   # <-- session-level gate
})
# ...then pull EVERY message of each matched session and filter in Python

An earlier fix widened this gate from "started yesterday" to "started within 3 days" — but a gate on session_started_at still drops any session that began more than 3 days ago, no matter how active it was yesterday. So the longest-running, highest-activity sessions were exactly the ones thrown away.

Of the in-window messages, the conversational user/assistant ones with real text are what the quiz actually uses: the old gate delivered ~15 of those; the fix delivers 72 — and from all 7 sessions, not just the 3 that happened to start yesterday.

4. Two problems this caused

  • Thin / "0 messages" quizzes. The generator got a sliver of the day (often stale meta), so questions were weak or it reported no data.
  • ~12-minute quiz generation. Warned about the gap, the agent fell back to a manual full-collection scan + bulk analysis of ~212 messages — the entire 725 s runtime was that fallback, not the quiz logic.

5. The fix — match the messages, server-side

Replace the find() + local Python loop with an aggregation pipeline that filters on the message timestamp and returns only the matching messages. No session_started_at gate exists anywhere.

db.sessions.aggregate([
  # sessions with ≥1 message in yesterday's KST window (matched on the message)
  { $match:  { "messages.timestamp": { $gte: start, $lt: end } } },
  { $unwind: "$messages" },
  # keep only the in-window user/assistant messages
  { $match:  { "messages.timestamp": { $gte: start, $lt: end },
               "messages.role": { $in: ["user","assistant"] } } },
  { $sort:   { "messages.timestamp": 1 } },
  # regroup by session for presentation
  { $group:  { _id: "$session_id", project: { $first: "$project" },
               device: { $first: "$device" },
               messages: { $push: { role: "$messages.role",
                                    content: "$messages.content" } } } },
  { $sort:   { _id: 1 } }
])

Timestamps are ISO-8601 strings, which sort lexicographically, so the range match works as a plain string comparison. The window is a half-open KST day [00:00 yesterday, 00:00 today) converted to UTC.

6. The principle

Let the database do the filtering. Ask for exactly the rows you need — don't drag whole documents over the wire and sift them on the client. The old path transferred entire messages arrays for every recent session, then discarded most in Python; the new path returns only the in-window messages, with no gate that can silently exclude the data you actually want.

7. Before / after

OLD find(session_started_at within 3d) ──▶ pull WHOLE sessions ──▶ filter messages in Python └─ drops sessions started >3d ago ⇒ 15 msgs, 3 sessions, ~12 min (fallback) NEW aggregate(match messages.timestamp) ──▶ unwind ──▶ match in-window ──▶ group by session └─ no session gate, server-side only ⇒ 72 msgs, 7 sessions, instant

Optional: a multikey index on messages.timestamp keeps the first $match fast as the collection grows (negligible at today's 213 sessions).
