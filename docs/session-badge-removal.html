Session badge removal — reverting /rename tooled 2026-07-30

The cyan session-name badge above the input box, why it survives the obvious fixes, and the toolkit script that removes it.

/rename has no inverse. The name lives in three stores, not one — and the third only exists for some sessions, which is why two correct-looking attempts failed silently.

Use it

python session_unname.py                     # the guided report (same as --plan)
python session_unname.py --plan [sid...]     # what is named, what to exit, gate, clear, resume
python session_unname.py --verify [sid...]   # THE GATE: exit 0 only if provably dead
python session_unname.py <sid> --analyze     # one session, all 3 stores, writes nothing
python session_unname.py <sid> --yes         # clear it (refuses while live)
claude --resume <sid>                        # bring it back, now unnamed

Or drive the whole thing with /unbadge (skill), which walks the five stages and refuses to clear anything until the gate passes.

The guided pipeline (/unbadge)

Removing a name is a gated process, because the two hard constraints are procedural, not textual: the target must be exited before the edit (a named session re-stamps its transcript every turn), and resumed after it (the badge is drawn from state loaded at startup, so a live process will not drop it mid-session).

1 LIST --plan which sessions carry an explicit name (2-store vs 3-store) 2 DETECT --plan which live pids hold them: pid, image, badge text, cwd, state 3 INSTRUCT --plan exit each one (interactive -> /exit; daemon -> claude agents) ---- user acts: exits those sessions ---- 4a GATE --verify exit 0 = provably dead - 1 = still live - 2 = UNKNOWN, refuse 4b CLEAR <sid> --yes only on exit 0; backs up, strips, verifies 5 RESTORE claude --resume <sid> badge clears on the fresh load

The gate fails closed. Two conditions make it refuse rather than approve: the process probe failing (no process list = liveness unknown), and any unreadable session record — a corrupt or mid-write record could belong to a live session, so treating it as absent would produce a false "all clear". Both return exit 2.

Pid alone is not a liveness marker. The OS recycles pids, so a dead session's pid can be reused by an unrelated process and read as "still live". The tool matches the running image name against the record and flags image is not claude as a probable recycled pid — visible rather than silently trusted.

The three stores

#PathLifetimeRole / action
1~/.claude/sessions/<pid>.jsonephemeral, per-pid The session record — a discovery registry so other processes can find live sessions. Not what the TUI reads to draw its own badge. No action: deleted on exit, recreated on resume with a derived name.
2~/.claude/projects/<slug>/<sid>.jsonlpersistent, per-session The transcript. Carries the name across restarts via two entry types (below). Re-stamped every turn while the session is explicitly named. Strip these entries.
3~/.claude/jobs/<first8-of-sid>/state.jsonpersistent, daemon only The job state (a supervisor's durable state). Survives process death and transcript strips, and re-applies the name on respawn. Remove name + nameSource only. This is the one that gets missed.

The two transcript entries that carry an explicit name:

{"type":"custom-title","customTitle":"<name>","sessionId":"..."}
{"type":"agent-name","agentName":"<name>","sessionId":"..."}

And the respawn line that re-applies it from store 3 — the mechanism behind the "it came back" failure:

...c.name && { name: c.name, nameSource: c.nameSource },

Which sessions have store 3 — origin, not usage

Only sessions born as background jobs carry a jobs entry (backend=daemon, template=bg). A session created headless keeps supervisor state permanently — even after a terminal is attached and it is used as an ordinary chat for days. A session started by typing claude never gets one.
Checkable in advance: does ~/.claude/jobs/<first-8-chars-of-sid>/ exist? yes → 3 stores · no → 2 stores. --analyze answers this for you.

Why it beat the two-store procedure twice: the process kept being killed and the transcript kept being cleaned, while the supervisor calmly re-applied the name it was holding for exactly that purpose. That wasn't a bug — it was a component doing its job.

nameSource has three values, not two

ValueMeaningBadge?
<absent>explicit name (in the session record, an explicit name omits the key)badge shown
"user"explicit /rename, as recorded in job statebadge shown
"auto" / "derived"auto-generated — slug(cwd) + short suffixno badge

Target end state = exactly what a fresh session looks like: name=<slug>-<xx>, nameSource=derived, zero transcript name entries, no name/nameSource in job state.

Order matters — two guards the script enforces

  • Exit first, and judge liveness by PID. Not by absence of a session record — records are per-pid and deleted on exit, so a record can be gone while a different pid still holds the session. The script checks live pids and refuses if the transcript was written in the last 20s (a live session with no record). --force overrides.
  • Stripping a live session is pointless. A named session re-stamps the transcript every turn, so the strip lasts seconds.
  • Resume with --resume <sid>, never --continue — the latter picks the most recent session in the folder and may grab the wrong one.

The grep trap (why the script parses JSON)

grep -c custom-title over a transcript counts every message that merely discusses the words. In the original investigation that produced a false "the process re-stamps every turn" conclusion — the count rose simply because the conversation kept writing the term.
The script prefilters on the substring (cheap) and then JSON-parses the line and compares obj["type"] exactly. It reports the discrepancy so the trap is visible, e.g.:
lines=10324  name entries=4 (custom-title=0, agent-name=4)
(21 line(s) merely MENTION those words — not counted; this is why grep over-counts)
Real: 4. Naive grep: 25.

Consider not doing it

The badge is cosmetic. The name is not — it is injected into the model's context each turn as a hint about the session's purpose. If the name is merely wrong, /rename <something-truthful> is the better fix: one command, no file surgery, and it improves the thing that actually matters. Use the script when you genuinely want no name.

Caveats

  • The scrollback still contains the literal /rename line you typed — the rename stays visible in history, it is simply no longer in effect.
  • The badge and the tab title are different consumers reading the name by different rules. Clearing the badge can leave a tab title in place (that is often the desirable end state: empty badge, tab still describing the work).
  • Both edited files are backed up as <name>.bak-unname-<timestamp> first. The transcript is your entire conversation history — the backup is not optional insurance, it is the point.
