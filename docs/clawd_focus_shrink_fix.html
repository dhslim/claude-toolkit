Clawd “Jump to Terminal” shrinks the window

Root-cause analysis, fix, and independent verification — clawd-focus patch
● RESOLVED ✓ INDEPENDENTLY VALIDATED commit 4bdcf00 · pushed 2026-06-24 · KST
TL;DR. Clicking Jump to Terminal on a maximized VS Code window (e.g. youmap) made it shrink. Cause was our own clawd-focus patch: its window-raise helper called ShowWindow(h, 9) — Win32 SW_RESTORE — unconditionally, and on a maximized window SW_RESTORE un-maximizes it. The fix is one guard: only restore when the window is minimized (if(IsIconic(h)) ShowWindow(h,9)). It was not caused by the Clawd-on-Desk update. Verified across all 3 extension copies, Clawd’s own native focus code, the live debug log, and git — by 5 independent checks.

1 · Symptom

From the Clawd on Desk Sessions window, pressing Jump to Terminal on the youmap session reliably took its VS Code window from maximized to a smaller, floating (“restored”) size. The terminal did get focused — but the window was resized as a side effect, every time.

2 · Background: two different “Clawd”s

The confusing part of this incident is that “Clawd” names two separate components, and the bug lived in one while an unrelated update touched the other:

Why the patch exists at all

VS Code multiplexes many project windows under one Code.exe PID, so Clawd’s native focus often lands on the wrong window. The clawd-focus patch makes the extension instance that owns the matching terminal raise its own window — matched by workspace-folder name against the window titles — via a warm, persistent PowerShell helper that compiles a tiny Win32 class once and stays resident for instant raises.

The focus flow (what happens on a click)

3 · Root cause

The helper’s Raise() called ShowWindow(h, 9) on every raise. 9 is the Win32 constant SW_RESTORE, whose documented behaviour is the trap:

nCmdShowConstantEffect
9SW_RESTORE“Activates and displays the window. If the window is minimized or maximized, the system restores it to its original size and position.”

So calling SW_RESTORE unconditionally is fine for a minimized window (un-minimizes it — desirable) but wrong for a maximized window: it “restores” it down to its previous floating size. That is precisely the shrink. It’s a classic Win32 pitfall — the correct pattern is to gate SW_RESTORE behind a minimized check.

The defect, in one line: … AttachThreadInput(cur,ft,true); ShowWindow(h,9); BringWindowToTop(h); … — no “is it minimized?” guard.

The bug had been latent in the patch since the v4 (“persistent warm helper”) rewrite. It only manifests when the raised window happens to be maximized, which is why it surfaced once windows were routinely kept maximized.

4 · It was not the Clawd update

An early hypothesis (mine) blamed a Clawd-on-Desk update. The evidence disproves it:

  • The update reverted the things bundled in the app — the app.asar byte-edits and the app-bundled extension copy — back to stock.
  • It did not touch …\.vscode\extensions\…\extension.js, the copy VS Code actually loads. That copy still carried our old, buggy patch (apply.ps1 later reported it “already patched, skipped”).
  • Clawd’s own native focus is already correctly guarded (see §6 validation) and never resizes a VS Code window.

So the shrink came entirely from our patch’s unconditional SW_RESTORE — present and firing regardless of the update. A secondary factor made it sticky: VS Code extension hosts don’t hot-reload on a disk change, so already-open windows kept running the old in-memory code (and an already-compiled PowerShell helper) until reloaded.

5 · The fix

Add the IsIconic import and guard the restore so it fires only when the window is minimized:

// buildHelperScript() — added DllImport
+ [DllImport("user32.dll")] public static extern bool IsIconic(IntPtr h);

// Raise() — the one-line guard
- … AttachThreadInput(cur,ft,true); ShowWindow(h,9); BringWindowToTop(h); SetForegroundWindow(h); …
+ … AttachThreadInput(cur,ft,true); if(IsIconic(h)) ShowWindow(h,9); BringWindowToTop(h); SetForegroundWindow(h); …
Maximized window → IsIconic is false → ShowWindow skipped → stays maximized. BringWindowToTop + SetForegroundWindow still raise it. No shrink.
Minimized window → IsIconic is true → ShowWindow(h,9) runs → un-minimizes. Restore still works.

Deployment (and a gotcha)

  1. Re-applied via apply.ps1 — restored everything the Clawd update wiped (asar broadcast 23460→23499, focus delay, no-flicker, Sessions width) and wrote the fixed extension to the app-bundled copy.
  2. apply.ps1 skipped the .vscode copy (“already patched”) — i.e. it refused to clobber the copy VS Code loads, which still held the old patch. We force-copied the fixed template over it.
  3. Reloaded the VS Code windows (Ctrl+Shift+P → “Developer: Reload Window”) so the host drops the stale code and a fresh PowerShell helper (with the guarded C#) spawns.

The Raise() body is byte-identical across all three (line 51), and the only ShowWindow(h,9) in each file is the guarded one:

public static void Raise(string sub){ IntPtr h=Find(sub); if(h==IntPtr.Zero) return;
  IntPtr fg=GetForegroundWindow(); uint p; uint ft=GetWindowThreadProcessId(fg,out p);
  uint cur=GetCurrentThreadId(); AttachThreadInput(cur,ft,true);
  if(IsIconic(h)) ShowWindow(h,9); BringWindowToTop(h); SetForegroundWindow(h);
  AttachThreadInput(cur,ft,false); }

6.2 — Clawd’s own native focus could not have caused it

Reading the app.asar binary confirmed stock Clawd never resizes a VS Code window:

  • Native focus is already guarded. The only ShowWindow in WinFocus.Focus() is if (IsIconic(hWnd)) ShowWindow(hWnd, 9) — restores only minimized windows.
  • Broadcast range = 23499 (the re-applied/widened range), not stock 23460 — confirming apply.ps1 took.
  • Every setBounds()/restore() in the asar targets Clawd’s own Electron windows (dashboard / settings / permission bubble), never a VS Code HWND.
  • Zero external-window resize primitives anywhere in the asar: MoveWindow=0, SetWindowPos=0, SW_MAXIMIZE=0, .maximize=0, .unmaximize=0.
Conclusion: the shrink could only have come from the extension’s Raise() — which is exactly what we fixed.

7 · Residual risks & future-proofing

The shrink is fixed, but the sweep flagged maintenance hazards worth closing:

RiskSevDetail & mitigation
apply.ps1 “skip if already patched” can strand an old patch MED Exactly what bit us on the .vscode copy. Make apply.ps1 re-write when the installed patched content differs from the current template (compare & force-update), instead of skipping any already-patched file.
Extension version-bump fragility (-0.1.1 hardcoded) MED If a future Clawd ships clawd-terminal-focus-0.1.2, apply.ps1 patches the wrong (old) folder and the stock new one loads → shrink returns. Fix: glob clawd.clawd-terminal-focus-*.
Clawd updates revert the app.asar edits LOW Broadcast range / no-flicker / delay / Sessions-width get wiped on each Clawd-on-Desk update (not the shrink). Routine: re-run apply.ps1 after updating Clawd.
