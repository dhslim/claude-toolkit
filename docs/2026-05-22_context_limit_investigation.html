"Context limit reached" — investigation & fix

A morning of intermittent Context limit reached / /clear to continue banners on the STT2 work session turned out to be two distinct bugs masquerading as the same error. This is the trace of how we untangled them and what we shipped.

2026-05-22 · session d7e890bd · proxy commits to follow · related: claude_proxy_explainer.html

TL;DR

  1. Two bugs, same banner. The "Context limit reached" red banner has at least two unrelated root causes: a malformed [1m] quota probe from CC, and the proxy's sliding-window halve not being aggressive enough on huge sessions.
  2. Bug B shipped a real fix. Replaced the proxy's "drop ratio of current" trim with slice-to-target using a hard cap constant. Always lands at a predictable size; no more 400s from over-cap.
  3. Bug A is deferred. Proxy correctly rewrites [1m] but Anthropic still 4xxs the rewritten quota probe. Workaround pending: short-circuit the probe at the proxy. CC self-recovers via retry meanwhile.
  4. Observability added. KST timestamps on every proxy log line, plus dedicated forensic dump files for both failure modes. If either bug recurs, the post-mortem data writes itself.

1 · The symptom

User's morning prompt on the STT2 session — >26 MB JSONL, near "Context low (0% remaining)" in CC's UI — landed this red banner immediately: 

okay so we need to turn on the FE 3000 again and check again
the issues we talked about before is working properly now ?
  └ Context limit reached · /clear to continue

After ~10 s, CC silently retried the same prompt and the real response came through. Same pattern repeated several times during the day across different prompts in the same session. CC's local accounting bar said 0% remaining, but /context told a different story.

The lie in the error message
CC shows "Context limit reached" for any non-200 response on the first attempt of a turn — even if the failure has nothing to do with context. This is the heart of the confusion. By the time the banner appears, you cannot tell from the UI whether you actually hit a context cap or whether something else is broken.

2 · Two distinct bugs underneath

BUG A DEFERRED

CC quota probe with malformed [1m] model id

On certain trigger moments (session start, near-context-low events), CC sends a tiny {"model": "claude-opus-4-7[1m]", "max_tokens": 1, "messages": [{"role": "user", "content": "quota"}]} probe.

claude-opus-4-7[1m] is not a valid Anthropic model id. Anthropic returns 404 (unknown model) or 429 (rate limit on the probe path).

CC misreads the 4xx as "Context limit reached," shows the banner, then silently retries the real messages call (which uses the bare id) — and succeeds.

Class: known (multiple GitHub issues). Specific mechanism: not in any public issue we found.
BUG B FIXED TODAY

Sliding-window halve insufficient on huge sessions

For a real /v1/messages with a 2.6 M-token body, the proxy's sliding-window SHIFT dropped 50% of current → landed at 1.46 M tokens. Still over Anthropic's 1 M cap → 400 "prompt is too long".

CC fires auto-compact (10 s), retries with a shorter list; proxy halves again → 761 K → 200 OK.

Same banner as Bug A. Same self-recovery. Different root cause.

Lived in the proxy since the Apr 14 refactor swapped TOKEN_BUDGET for SHIFT_RATIO.

3 · Investigation timeline

First framing
"Did our recent fix break something?"
User saw API Error: Unable to connect to API (ConnectionRefused) in a screenshot. Initial hypothesis: the morning's [1m] rewrite commit broke proxy startup. False. Proxy was up; proxy.err.log was stale from April. ConnectionRefused was a transient blip during a manual restart window.
Re-anchor
Old screenshots also showed "Context limit reached"
The banner kept appearing even after the proxy was confirmed healthy on PID 7996 (loaded with the [1m] fix). So the fix wasn't sufficient.
Add forensic dump #1
Capture the rewritten request + Anthropic's response
Modified proxy to write proxy_1m_dump.json on the next [1m]-rewrite 4xx. Trigger: fresh CC session. Captured a real probe at 10:49 KST.
First "aha"
The request isn't a "1M context probe" — it's a quota check
The dump body was literally {"messages": [{"role": "user", "content": "quota"}], "max_tokens": 1}. CC just happens to tag every quota check with [1m] by mistake. The rewrite to bare id + beta header is correct — but Anthropic's quota path rate-limits it (429) or doesn't recognize the combination (404 with empty body).
Separate banner instance
An STT2 prompt produced the banner with a totally different cause
Traced via proxy.log: 9.3 MB body, 5,356 msgs, SHIFT trimmed 2.64 M → 1.46 M tok → Anthropic 400 "prompt is too long: 1458123 > 1000000". The sliding window's halve undershoots when starting size is over ~2 M tok. The next request (after CC auto-compact) shifted again to 761 K → 200 OK. Bug B identified.
User's mental model challenge
"I'm pretty sure the 0.5 means 'fraction of cap', not 'fraction of current'?"
Checked git history. Pre-refactor (1ff4a94, Mar 30) used TOKEN_BUDGET = 700 K with a binary-search-to-fit, which IS user's mental model. Refactor fec7ffc (Apr 14) swapped to threshold+ratio for cache stability — at the cost of unpredictable trim sizes. User's instinct was right about the original design; the current behavior was the regression.
Design synthesis
Slice-to-target: combine the predictability of pre-refactor with the cache-stability of current
Three explicit constants: HARD_CAP_TOKENS, SHIFT_TRIGGER, SHIFT_RATIO. SHIFT_RATIO now means "fraction of HARD_CAP to settle at" (target), not "fraction of current to drop." One slice, always lands at the target, regardless of starting size. Plus a safety re-shift loop for when the per-group estimate undershoots.
Ship + instrument
Slice-to-target implemented; observability added for both bugs
Bug B's fix is live (proxy started 14:01 KST, PID 38664 — though see "manual restart" note below). KST timestamps on every proxy log line; proxy_over_cap_dump.json mirrors the [1m] dump for Bug B recurrences. Bug A's short-circuit fix deferred — CC's auto-retry papers over it, and the proper fix needs more design.

4 · The Bug B fix: slice-to-target sliding window

The three constants

ConstantDefaultRole
HARD_CAP_TOKENS 1_000_000 Anthropic's actual ceiling. Anything over → 400. Immutable; this is the API's number, not ours.
SHIFT_TRIGGER 700_000 The count_tokens value above which a shift fires. Leaves ~300 K headroom under the cap.
SHIFT_RATIO 0.5 Target size as a fraction of HARD_CAP. 0.5 × 1M = 500K. One slice from any starting size lands here.

Three designs side by side

Pre-refactor (Mar 30)

One constant: TOKEN_BUDGET

Binary search every turn: find the largest n such that "keep last n groups" fits under TOKEN_BUDGET.

Always under cap. But trims every turn → byte prefix shifts every turn → cache miss every turn → 3–5 min slow turns.

Current (Apr 14 – this morning)

Two: SHIFT_THRESHOLD + SHIFT_RATIO

Trim only when over threshold. When triggered, drop SHIFT_RATIO × remaining tokens. 0.5 = halve.

Cache-stable between shifts. But result is unpredictable — halving a 2.6 M-token request lands at 1.3 M, still over cap → 400.

New (today)

Three: HARD_CAP + SHIFT_TRIGGER + SHIFT_RATIO

Trim only when over trigger. When triggered, slice down to HARD_CAP × SHIFT_RATIO tokens. Safety loop verifies and shifts further if estimate undershot.

Always under cap. Always at predictable size. Cache-stable between shifts. Best of both.

5 · Observability added NEW

So that future incidents post-mortem themselves:

WhatWhereWhy
KST timestamps on every proxy log line proxy.log — format [YYYY-MM-DD HH:MM:SS KST] [proxy] … Lets you correlate banner moments in CC chat to proxy events. Previously the proxy log had no times, just ordered events.
proxy_1m_dump.json Project root Captures the full request + Anthropic response for the next [1m]-rewrite 4xx. Survives until next overwrite.
proxy_over_cap_dump.json Project root Captures the same for any 400 "prompt is too long". If Bug B's fix ever fails, this fires.
↻ safety re-shift log line proxy.log Fires only when the per-group estimate undershot and the safety loop had to shift further. Greppable for tuning the 1.26x under-report constant.
Re-derived key finding (kept)
Anthropic's /v1/messages/count_tokens systematically under-reports vs. the real processing token count by ~1.26× for prose/code (more for code-dense). We observed a 413 at count_tokens=791,826 on 2026-04-14. This is why HARD_CAP × 0.5 = 500K target is genuinely safe: 500K × 1.3 ≈ 650K real ≪ 1M.

7 · Lessons

  1. "Same symptom" ≠ "same bug." The banner is overloaded — any 4xx triggers it. Diagnosing required separating the failure modes from the UX.
  2. Read the existing investigation notes first. The proxy file's docstrings and inline comments held key findings (the 1.26× under-report, the cache_control ordering rule). Skimming those before proposing a fix would have saved redoing the design rationale.
  3. Production refactors trade. The Apr 14 swap from TOKEN_BUDGET → SHIFT_RATIO won cache stability and lost predictability. The fix isn't "revert" — it's combine both with a third constant.
  4. Don't auto-restart the proxy from inside a CC session. Disrupts every active session on the machine. Wrapper handles cold starts gracefully when a fresh terminal opens.
  5. Capture forensics before assuming. The proxy_1m_dump.json revealed the probe was a "quota" check, not a "1M context" probe. The earlier commit message I wrote about Bug A was partially wrong as a result.
